## 2. 推荐执行模式

**路线 A：当前会话工具自动调度。** 后续获得生产授权后，由 Codex 自动读取资料、编写 Prompt、逐只调用 `image_gen__imagegen`，设 `transparent_background: true`；新图不附带参考图参数。有已落库且确认为风格基准的图时，才使用工具支持的参考图机制。每只一份任务，不让模型在一张图里画十二只再裁切。结果依工具返回资源，经受支持的资源传输接口保存真实二进制，先落到暂存区，再验证格式。若只得到界面图片而无可下载二进制，立即记录传输阻塞，不能让用户逐张截图或拿空文件代替。

该工具属于会话工具，不是可直接从 Python 调用的本地 CLI 或 shell SDK；不得伪造同名 HTTP 接口。当前 schema 返回 image_url，但不保证本地文件路径或具体 URL 传输形式，适配器须识别实际返回类型，数据 URL 应经可靠文件通道解码，临时 HTTPS 资源只通过支持的代理下载，绝不把含凭据链接写进日志。未实测前不能承诺完全无人值守运行 120 次、固定并发或固定尺寸。工具未暴露模型 ID、seed、费用和请求 ID时如实记 null/未提供，并记录工具名，不虚构模型元数据。

**路线 B：独立 API 程序（长期自动续跑推荐）。** 在用户选定供应商、模型并明确授权费用后，采用支持原生透明 PNG 的官方图像生成 API；Python 工作者统一处理队列、限流、重试、元数据、PNG 检查与 Git。模型可配置，启动时对照供应商最新官方文档核对可用模型、透明输出参数、速率和价格，不在本方案中假定具体型号或单张价格。无需用户复制 Prompt、下载、改名、上传。当前路线 A 可以作为先行方案，路线 B 是可跨会话重复运行的自动化目标；两条路线都需先做六图基准，不直接跳过审核。

## 4. 数据读取与独立 Prompt 编排

1. 从 BREED_DATA 的八列事实表解析 120 条记录，不把后面的 88 条拟人旁白当作第二批犬种；校验 ID、中文、英文、slug 唯一，并与 ASSET_MANIFEST 关联。
2. 从 ILLUSTRATION_GUIDE V1.1 读取统一风格、线条、暗面、纸感、1024 输出与等比适配约束；从 ILLUSTRATION_REVIEW 读取 B001/B002/B003/B004/B005/B007 的具体修改要求。原始六份 V1.0 Prompt 仅为历史参考，不直接重新执行。
3. 为每只建立独立造型档案：耳形、口吻、头形、身长腿长、尾型、被毛、配色、姿态、对应人格（如有）。已有犬种资料对部分形态描述不足，不能仅按大类填同一身体。由 AI 在单独的生产档案补充保守形态设定，记录依据/不确定项；不改 BREED_DATA。缺少可靠依据或与源资料冲突时暂停该犬种核验，而非猜造并跳过检查。造型档案需要风格和犬种识别检查，不能称为已权威核验的生物事实。
4. Prompt = 完整 DPL-ILL-1.1 公共约束＋该犬种造型档案＋独立姿态/色彩＋逐犬修改要求＋禁止项。保存全文、版本及 SHA256，要求至少三项结构辨识差异，不只是换色。Prompt 由 AI 自动生成，不交给用户逐条拼接。
5. 推荐版本键 `{breed_id}-full-v02`（既有六种修订）或 `{breed_id}-full-v01`（首次生产），加 `style_version=DPL-ILL-1.1`；版本名仅在实际任务创建后登记，当前不预填生成日志。

## 5. 批次、限流与断点续跑

保留现有审核门槛：第一轮 6 张基准（自动执行，用户只看合版和反馈）；第二轮为 ILLUSTRATION_GUIDE 已选定的 12 张；第三轮剩余 102 张，通常每批 10–12 张，尾批可少于 10 张。例如第三轮按 12 张分为 8 批＋末批 6 张。32 张肖像在对应全身图验收后另排队，不混入 120 张全身计数。

每批 10–12 张是队列规模，不意味着同时发起 12 个请求。建议先串行，确认工具/账户限制后最多低并发 1–2；遵守实际速率、Retry-After、上下文和预算。每批完成自动校验、合版、Git 同步后暂停等待一次批量审核；用户不需要手工复制或上传。用户可一次标注整批认可或需要重做的 Breed ID，但自动检查不提升人工批准状态。

运行时内部状态：queued → requesting → raw_saved → processed → qc_pass/qc_fail → synced；人工审核另存 pending/reviewed/approved，不将内部状态原样写成清单新枚举。ASSET_MANIFEST 仍按现有 PLANNED/GENERATED/REVIEWED/APPROVED 和“所需资产最低进度”汇总：正式犬格仅有全身图时，肖像尚无则总状态仍可能 PLANNED，必须在逐文件记录和“实际文件”栏说明全身已生成，不能因此反复生成同一全身图。

断点键为 `breed_id + asset_kind + prompt_sha256 + model/config版本`。每步先检查既有文件、记录和 SHA256：文件完整且一致就跳过；有文件但无记录则隔离核对，不覆盖、不盲目重生成；记录有文件而文件缺失时先尝试恢复原产物。进程锁避免两个工作者处理同一犬种，原子写入记录，发布用禁止覆盖的原子操作。每种保留版本化候选图，正式路径已有内容则只报告冲突；修改版另存 v02/v03，待明确选版后执行受控替换，绝不默认覆盖已生成图片。

网络/429/明确可重试服务错误采用指数退避和随机抖动，最多 3 次尝试（含首次），服从预算与供应商建议。认证/权限/参数/策略拒绝不重复重试、不绕过。超时且可能已在服务端生成时标记 outcome_unknown：先按供应商真实支持的请求查询/幂等机制恢复；不假设所有端点有幂等保证，无法确认则暂停该任务，避免重复计费。生成已成功而保存、处理或 Git 失败只重试对应步骤，不再次调用模型。

## 6. 自动处理与透明度

保存供应商真实原始图/高清母版，记录来源哈希；不覆盖源图。确认解码安全、格式与尺寸后，读取 alpha 包围盒，按最长边约 819px 等比缩放到 1024×1024 RGBA 透明画布，平移对齐；站姿尽量脚底 y≈920，坐姿按独立构图。不可改变宽高比，原图已经裁耳尾或主体低清时退回，不用补透明边冒充结构修复。

优先原生透明生成。把 RGB 转成 RGBA 并令所有像素 alpha=255 只得到不透明图，不算去底。纯色阈值扣白可能误删白毛，不能作为默认方案。当前无本地去底模型；若后续需要，先选定可信去底模型/工具及许可与权重下载，使用独立处理适配器保留源图、遮罩和参数，再以三底合版人工复核白毛、卷毛、细腿与尾尖。工具不可用或审核不通过则标 qc_fail，不交付假透明。

处理目标：外部 alpha=0、主体内部 alpha=255、仅轮廓抗锯齿允许中间 alpha。不能全图二值化造成锯齿，也不能仅把半透明内部强行填满当作语义正确。后续处理需检查内部孔洞与自然轮廓间隙，必要时回到生成/真实蒙版修订流程。图像编辑后端遵循可用图像工具的使用约束；纯格式/尺寸/alpha 测量可由 Pillow 处理，不用几何图形重画犬只。

## 7. 自动质量检查与合版

| 项目 | 自动判定或信号 | 不能替代的审核 |
|---|---|---|
| 文件与关联 | PNG 文件头、完整解码、1024×1024、RGBA；slug 路径与任务 ID 严格一致 | 图内是否真为目标犬种 |
| Alpha | 外围安全区透明，非空且非全透明；四角透明不足以代表背景合格；统计主体内半透明比例与孔洞 | 白毛是否误删，真实肢体间空隙是否被填死 |
| 裁切与占比 | alpha 包围盒是否触边、安全边是否约 10%、最长边是否约 80%；原始图触边也需标记 | 透明留白内仍可能缺耳或尾尖 |
| 不拉伸 | 记录统一缩放因子，宽高比保持一致 | 原始生成形态是否正确 |
| 重复 | 原文件/正式文件 SHA256 精确查重，像素哈希查同内容不同编码；感知哈希标近似重复 | 相似姿态不一定是抄图，阈值需六图基准校准 |
| 轮廓和颜色 | 连通分量、面积、深色轮廓占比、主色聚类与边缘密度异常警告 | 连通分量数不等于四肢数；自然纸感不等于噪声，犬种结构需视觉识别 |
| 语义/画风 | 可用时使用视觉模型检查耳口鼻、尾型、额外肢体、IP 相似与参考基准一致性 | AI 视觉评估不算人工批准，也不能保证无版权问题 |

几何阈值初设最长边约 78–82%，安全边优先不小于约 10%（存在冲突时以完整主体和安全边优先），首批真实图片后校准；不为满足阈值改造犬种比例。轮廓、色数、纸感阈值不能在没有图时假称实测通过。异常图隔离、记录原因，不自动发布为合格正式图。

每批由 Pillow 生成一张合版，最多 12 格（如 4×3），标 Breed ID、中文名、候选版本与 QC 摘要；主体叠在 paper 上，另附 ink/mist 三底边缘检视，标签只在合版中，不写进透明 PNG。批次明细关联原图，让用户一次查看整批而非逐张下载上传。合版为预览，不替代每只独立 1024 PNG。

## 9. 每批 GitHub 自动同步

仅在 `iris0914ovo/DogLab`、分支 `work` 执行；首先核对 origin、分支、未提交内容与远程变化。用持久化逐文件记录更新 ASSET_MANIFEST 的真实文件、审核意见和汇总状态；成功图像与失败明细分别记录，不把整批一律标完成。生产重试不依赖 Markdown 汇总状态，而依赖逐文件证据。

每批在检查通过后只暂存该批的独立 PNG、合版、元数据及清单差异，核对数量与二进制尺寸，创建带 batch ID 的 Git Commit，`git push origin work`。失败时记录真实原因并停在 sync_failed，不强制推送、不覆盖 main、不重生成图片。若远程前进，先检查分歧并安全整合；冲突不自动覆盖其他人更改。

上传验证分两层：先 `git ls-remote origin refs/heads/work` 确认远程包含本批提交（通常远程头等于本地头；若又有后续提交，则校验本提交是远程祖先），再在独立临时 Git 对象库中读取远程 work 的树与目标 PNG blob，逐文件核对路径、大小和 SHA256。这样验证远端实际提交内容，而不只检查本地文件或 git push 的退出码。每批报告原生 GitHub 文件链接和提交链接。GitHub API 另有认证范围，不因 HTTPS Git 成功就假设 REST 写权限。
